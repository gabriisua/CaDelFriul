# Codebase Concerns

**Analysis Date:** 2026-07-08

## Tech Debt

### No Test Infrastructure

- **Issue:** The project has no test framework configured (no `jest.config.*`, `vitest.config.*`, or any test file). The `package.json` has no test scripts beyond what was scaffolded. `tsconfig.json` includes `/coverage` in `.gitignore` but nothing generates coverage data.
- **Files:** `package.json`
- **Impact:** Any code written cannot be validated automatically. Regression risk is high for even trivial changes. No path to CI enforcement.
- **Fix approach:** Add a test runner (Vitest recommended for Vite/Next.js), configure `@testing-library/react` for component tests, and create at least a smoke test for the root layout and page. Add `test` and `test:run` scripts to `package.json`.

### No Environment Variable Configuration

- **Issue:** No `.env.local`, `.env.development`, `.env.production`, or `.env.example` file exists. The `.gitignore` blocks `.env*` from being committed (correct), but there is no `.env.example` to document required variables.
- **Files:** `.gitignore` (line 34), entire repo
- **Impact:** When API keys, database URLs, or other secrets are needed, there is no documented template. Developers must reverse-engineer required variables from code or documentation.
- **Fix approach:** Create `.env.example` with documented placeholder values for any environment variables the app requires. Add a pre-commit or pre-push hook that warns if `.env.example` is present but actual env vars are missing.

### Missing TypeScript Strict Flags

- **Issue:** `tsconfig.json` enables `"strict": true` (good) but omits additional safety flags: `noUnusedLocals`, `noUnusedParameters`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `forceConsistentCasingInFileNames`.
- **Files:** `tsconfig.json`
- **Impact:** Unused variables and parameters compile silently. Unsafe index access on objects/types is not caught at compile time.
- **Fix approach:** Add `"noUnusedLocals": true`, `"noUnusedParameters": true`, `"noUncheckedIndexedAccess": true`, and `"forceConsistentCasingInFileNames": true` to `tsconfig.json` compilerOptions.

### Stale Boilerplate Metadata

- **Issue:** The root layout's metadata still reads `title: "Create Next App"` and `description: "Generated by create next app"`. The `README.md` is the default `create-next-app` template.
- **Files:** `src/app/layout.tsx` (lines 16–17), `README.md`
- **Impact:** Production deployment would expose placeholder branding in document title and meta description. README does not describe the actual project.
- **Fix approach:** Update metadata in `src/app/layout.tsx` to reflect the project name ("CaDelFriul" / fe-cadelfriul). Replace `README.md` with project-specific documentation.

## Security Considerations

### Transitive PostCSS Vulnerability

- **Risk:** `npm audit` reports a **moderate severity** XSS vulnerability in PostCSS (versions < 8.5.10). The vulnerable package is a transitive dependency of `next@16.2.10` at `node_modules/next/node_modules/postcss`. Advisory: GHSA-qx2v-qp2m-jg93 — "PostCSS has XSS via Unescaped `</style>` in its CSS Stringify Output."
- **Files:** `package.json` (dependency chain: next → postcss), `node_modules/next/node_modules/postcss`
- **Current mitigation:** None. The `--force` fix would downgrade Next.js to 9.3.3, which is not a viable fix. The vulnerability is in PostCSS stringify and would require malicious CSS input to exploit, but it is unpatched.
- **Recommendations:** Monitor the Next.js issue tracker for a patch release that bumps the internal PostCSS dependency. Consider pinning Next.js to a version with a fixed PostCSS once available. If user-generated CSS content is ever processed, mitigate by sanitizing inputs.

### No Environment Validation

- **Risk:** No `.env` files exist yet, so no secrets are exposed. However, there is no pattern for validating required environment variables at startup (e.g., using `zod` or a custom `env.ts`). Once external services are integrated, missing env vars could fail silently or at unexpected points.
- **Files:** Entire project
- **Current mitigation:** None.
- **Recommendations:** Create `src/lib/env.ts` (or similar) that validates `process.env` entries against a schema at app startup. Add `.env.example` with documented variables.

### Cross-Origin Dev Server Protection

- **Risk:** The dev server already logged `Blocked cross-origin request to Next.js dev resource /_next/webpack-hmr from "172.16.70.93"`. This is a safety feature, but if remote debugging is needed, `allowedDevOrigins` must be explicitly configured, which widens the attack surface.
- **Files:** `.next/dev/logs/next-development.log`, `next.config.ts`
- **Current mitigation:** Default block is active. No `allowedDevOrigins` configured yet (safe default).
- **Recommendations:** Keep `allowedDevOrigins` unconfigured unless remote debugging is required. If added, scope it to specific IPs, not wildcards.

## Fragile Areas

### React Compiler Configuration

- **Files:** `next.config.ts` (line 5: `reactCompiler: true`), `package.json` (line 21: `"babel-plugin-react-compiler": "1.0.0"`)
- **Why fragile:** The React Compiler (`reactCompiler: true`) is enabled in `next.config.ts`, and the Babel plugin is listed in `devDependencies`. However, in Next.js 16, the React Compiler integration may require additional configuration or specific versions to work correctly. The `babel-plugin-react-compiler` version `1.0.0` is specified un-pinned in the dependency declaration. If the compiler silently fails or is misconfigured, there will be no observable build error — it would simply not optimize.
- **Safe modification:** Before adding more components, verify the React Compiler is actively being invoked by checking the build output for compiler diagnostics. Pin the babel plugin to an exact version. Consider removing `reactCompiler: true` if the compiler is not yet needed.
- **Test coverage:** None — no tests exist to validate compiled output behavior.

### Fresh Project State

- **Files:** Entire repository (single commit `773ecc8`, no branches, no tags)
- **Why fragile:** The project has exactly one commit and no development history. Any code change is the first custom change. There is no rollback safety net beyond `git reset`. No CI pipeline exists to catch breakage.
- **Safe modification:** Commit frequently after the initial setup. Establish a CI pipeline (GitHub Actions) before adding business logic.
- **Test coverage:** Zero test coverage across 100% of the codebase.

## Scaling Limits

### No Application Architecture

- **Current capacity:** Zero. The project has a `src/` directory with a single `app/` folder containing only the scaffolded route. There is no `src/components/`, `src/lib/`, `src/hooks/`, `src/types/`, or `src/app/api/` directory.
- **Limit:** As soon as the first feature is added, files will be placed ad-hoc unless a directory structure is established. This leads to architecture decay within the first few commits.
- **Scaling path:** Define a directory structure upfront (e.g., `src/components/ui/`, `src/features/`, `src/lib/`, `src/hooks/`, `src/types/`, `src/app/api/`). Establish barrel exports and module boundaries early.

### No API Route Infrastructure

- **Current capacity:** No backend API routes exist (`src/app/api/` is absent). No server actions, no route handlers.
- **Limit:** The application cannot serve dynamic data or accept form submissions without adding these patterns from scratch with no existing pattern to follow.
- **Scaling path:** Create a `src/app/api/` directory with a health-check route as a template. Add a server action pattern file before implementing feature endpoints.

## Dependencies at Risk

### PostCSS (transitive via Next.js)

- **Risk:** Moderate severity XSS vulnerability, unpatched in the version bundled with Next.js 16.2.10. Cannot be fixed with `npm audit fix` without breaking Next.js (the `--force` fix would downgrade to Next.js 9.3.3, a 7-year-old version).
- **Impact:** If user-provided CSS is ever processed through PostCSS, XSS is possible. Currently no user CSS input is handled, so risk is theoretical.
- **Migration plan:** Monitor Next.js releases. Update to the latest Next.js patch when available. The advisory is fixed in PostCSS >=8.5.10.

### eslint 9 vs 10

- **Risk:** ESLint 9.39.4 is installed, but ESLint 10.6.0 is the latest. The flat config format (`eslint.config.mjs`) used here was introduced in ESLint 9 and migrated in ESLint 10. A future `create-next-app` will likely scaffold with ESLint 10. Staying on 9 creates a migration task.
- **Impact:** None immediately, but the gap will grow. Plugin compatibility may shift.
- **Migration plan:** Upgrade to ESLint 10 when `eslint-config-next` 16.2.x or later supports it.

### TypeScript 5 vs 6

- **Risk:** TypeScript 5.9.3 installed, TypeScript 6.0.3 is the latest. Since this is a brand-new project, starting with TS 6 would be ideal to avoid a near-term migration.
- **Impact:** Minor. TS 6 may introduce new syntax or strictness that requires code changes later.
- **Migration plan:** Upgrade to TypeScript 6 after verifying `eslint-config-next` and `@types/*` packages are compatible.

### React 19.2.4 vs 19.2.7

- **Risk:** React 19.2.4 is installed; 19.2.7 is latest. Patch releases may contain bug fixes relevant to React 19 features used (e.g., Server Components, Actions).
- **Impact:** Low risk of missing bug fixes. Should be updated.
- **Migration plan:** Run `npm update react react-dom` to get the latest patch.

### @types/node 20 vs 26

- **Risk:** `@types/node@20.19.43` is installed; `26.1.1` is latest. Node.js types for the LTS version (22.x) or current (24.x) are not aligned.
- **Impact:** Type definitions may not match the actual Node.js runtime APIs.
- **Migration plan:** Align with the actual Node.js version used in development and deployment.
